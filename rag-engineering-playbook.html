An end-to-end framework for designing, evaluating and operating Retrieval-Augmented Generation systems. Use it to explain the architecture clearly without implying that every component has already been implemented in EvidMatch.

01 / SYSTEM VIEW

The complete lifecycle

Think in four layers: prepare knowledge offline, answer queries online, optionally orchestrate tools, then evaluate and operate the whole system.

Offline pipeline

Prepare the knowledge base

Ingestion → parsing → cleaning → chunking → metadata → embeddings → indexing. This work is usually asynchronous and repeated when source content changes.

Online pipeline

Answer a user query

Understand query → retrieve → filter/rerank → construct context → prompt → generate → validate and cite. This path is latency-sensitive.

Agentic capabilities

Call tools when needed

Tool calling is not a mandatory RAG stage. An agent may use search, databases or business APIs to retrieve fresh data or perform an authorised action.

Evaluation & operations

Prove it works in production

Measure retrieval, answer quality, permissions, task success, latency, cost and failure rates. Add monitoring, auditability and recovery.

Keep the concepts distinct: RAG retrieves relevant knowledge to ground a response. Tool calling invokes an external capability. An agent plans and coordinates one or more steps. Agentic RAG combines these patterns, but not every RAG system needs an agent.
02 / OFFLINE PIPELINE

Ingestion, chunking and indexing

The quality of retrieval is constrained by the quality and structure of the data entering the index.

1. Data ingestion

Acquire data from approved sources: document stores, APIs, databases, connectors or ETL pipelines. Capture source identity, ownership and update events.

Design questions: Which sources are in scope? How frequently do they change? What is the expected volume? Are there source-side permissions?

2. Parsing and extraction

Extract usable text and structure from PDF, Word, HTML, spreadsheets and scanned documents. Apply OCR where required. Preserve headings, tables, page numbers and document boundaries where possible.

Failure mode: a PDF parser silently drops table columns or reading order, so the indexed text no longer represents the source accurately.

3. Cleaning and normalisation

Remove navigation noise, duplicated boilerplate and malformed characters; normalise formats and dates. Retain the original source and a traceable version rather than destroying provenance.

4. Chunking

Split documents into retrievable units. Common approaches include fixed-size with overlap, semantic chunking and structure-aware chunking based on headings or sections.

Choose chunk size based on document structure, retrieval quality and model context. Too large reduces precision; too small can lose context. Preserve page, heading and parent-document references.

5. Metadata enrichment

Attach document ID, chunk ID, source, page/section, timestamp, version, department, classification and access-control attributes. Metadata supports filtering, citations, freshness and governance.

6. Embedding generation

Convert each chunk into a numerical vector using an embedding model. The vector represents semantic features; it is not a summary or a translation. Track the model and version used so embeddings can be reproduced or migrated.

7. Indexing and storage

Store searchable vectors in a vector index, exact terms in a lexical index such as BM25, and filterable attributes in a metadata store. Some platforms combine these capabilities.

Embedding ≠ indexing: embedding creates the representation; indexing organises representations and terms so queries can find them efficiently.

Incremental updates

Detect new, changed, deleted and unchanged documents. Use stable IDs and content hashes to avoid unnecessary reprocessing. Update or remove stale chunks and keep index versions consistent.

03 / ONLINE PIPELINE

Retrieval to grounded answer

The online path should retrieve relevant evidence, enforce permissions, fit the evidence into a controlled context and generate a response that stays within that evidence.

8. Query understanding

Identify intent, entities, time range, requested output and whether the question is answerable from the indexed knowledge. Apply query rewriting, expansion or decomposition when useful.

9. Retrieval

  • Vector search: semantic similarity; useful when wording differs.
  • Keyword/BM25: exact terms, names, IDs, dates and technical identifiers.
  • Hybrid search: combines lexical and semantic signals.

Choose based on the corpus and query types; do not assume vector search alone is always best.

10. Filtering and reranking

Apply metadata filters and access-control checks, then optionally rerank candidates with a relevance model. A reranker improves ordering; it does not replace permission enforcement.

Security invariant: unauthorised content must be excluded before it can enter the model context.

11. Context construction

Select top-K evidence within a token budget. Deduplicate overlapping chunks, preserve useful ordering and include source metadata. More context is not automatically better.

12. Prompt construction

Combine system instructions, user query and retrieved evidence. Tell the model to answer from the supplied sources, distinguish facts from inference, cite evidence and abstain when support is insufficient. Treat retrieved documents as untrusted data, not instructions.

13. Generation and validation

Generate the answer, then validate format, citations and policy constraints. Check whether citations actually support the associated claims. If evidence is weak or conflicting, qualify the answer or abstain.

Diagnose failures by stage: no relevant source retrieved = retrieval failure; relevant source retrieved but answer misstates it = generation/faithfulness failure; answer is correct but cites the wrong source = citation failure. These require different fixes.
04 / TOOL CALLING

Where tools and agents fit

A RAG system answers from retrieved knowledge. A tool-enabled system can also query live systems or take actions, subject to validation and authorisation.

Tool-calling controls

  • Use typed schemas and validate arguments.
  • Enforce user identity and permissions at the tool boundary.
  • Use timeouts, bounded retries and idempotency for mutations.
  • Require confirmation or human approval for consequential actions.
  • Record tool selection, arguments, result and execution status in audit logs.

Example: enterprise assistant

A user asks for correspondence about a case during a date range. The agent calls an authorised email-search tool, retrieves matching messages, optionally uses RAG to ground the summary in those messages, then returns a cited summary. Sending a message or changing a record would be a separate action requiring the relevant permission and potentially confirmation.

Useful distinction for interviews: MCP standardises how AI applications connect to tools and context providers; it does not itself decide which tool should be called or guarantee that the action is safe. The application still owns identity, authorisation, validation and audit.
05 / EVALUATION

Evaluate each layer separately

Build a representative, versioned test set with expected evidence and expected behaviour. Evaluate component quality and end-to-end task success.

LayerWhat to measureExample metrics / checks
Ingestion & parsingDid we ingest and extract the source correctly?Ingestion success, extraction accuracy, missing-page/table checks
RetrievalDid we find the relevant evidence?Recall@K, Precision@K, MRR, NDCG
GenerationIs the answer correct and supported by retrieved evidence?Correctness, faithfulness / groundedness, unsupported-claim rate
CitationsDo sources support the claims they are attached to?Citation precision, citation coverage
Abstention & safetyDoes the system decline when evidence or permission is insufficient?Appropriate abstention, false refusal, unauthorised retrieval (target zero)
Tool useDid it choose and execute the right tool safely?Tool-selection accuracy, argument validity, task success, policy violations
OperationsIs it usable and sustainable?p50/p95 latency, throughput, error rate, cost per task

Retrieval evaluation

Compare retrieved chunks with labelled relevant evidence. Recall@K asks whether relevant evidence appears in the top K; MRR rewards placing the first relevant result higher; NDCG accounts for graded relevance and ranking position.

Answer evaluation

Judge whether the final answer is factually correct, faithful to the retrieved context, appropriately qualified and accurately cited. A strong retrieval score does not guarantee a good answer.

Evaluation discipline: maintain a fixed baseline set, include answerable and unanswerable cases, add adversarial and permission-boundary cases, record model/prompt/index versions, and rerun the suite after changes. Human review remains important for high-impact use cases.

Evidence from EvidMatch — describe the scope accurately

The current work uses text-embedding-3-small, similarity threshold 0.30 and K=5, with retrieval metrics such as Hit@1, Hit@5 and MRR plus answer-layer refusal checks. The initial labelled sets were small (27 cases for one profile and 14 for another), so present the numbers as early baselines, not as proof of a mature production evaluation platform. A structured facts block for identity/location removed a location-related false-refusal pattern without changing the production RAG configuration.

06 / PRODUCTION ENGINEERING

Security, reliability and operations

Enterprise RAG is not just a prompt and a vector database. It is a data and application system with security, lifecycle and operational responsibilities.

Access control

Carry identity and ACL/RBAC attributes through ingestion and retrieval. Apply permission filters before context construction. Test cross-user and cross-tenant isolation; unauthorised retrieval should be zero.

Provenance & audit

Keep source IDs, versions, timestamps and citations. Log which evidence was retrieved and which tools were invoked so outcomes can be investigated.

Async processing

Use queues and background workers for long-running parse/embed/index jobs. Expose job status and avoid tying a large ingestion task to a user-facing request.

Retry & idempotency

Use bounded retries with exponential backoff for transient failures. Make jobs safe to retry without duplicate or inconsistent records. Distinguish transient from permanent errors.

Freshness & versioning

Track document, parser, chunking and embedding-model versions. Handle update and delete events; plan re-embedding when models or schemas change.

Observability

Trace query ID, retrieved chunk IDs/scores, model and prompt version, token usage, tool calls, latency, errors and citation output. Monitor quality and cost trends, not just uptime.

Example asynchronous ingestion flow

Upload / source event → job queue → worker → parse and clean → chunk and enrich → embed → update indexes → mark job complete. Add retries, dead-letter handling, idempotency, progress status and audit events around the stages.

07 / CAPACITY & COST

Estimate before you scale

Estimate the workload from document volume, chunking, embedding dimensions, query volume, context size and concurrency. Then validate assumptions with load tests and observed metrics.

Storage sizing example

Assume 1 million documents, 20 chunks per document and 1,536-dimensional float32 embeddings:

  • Chunks: 1,000,000 × 20 = 20 million vectors.
  • Raw vector bytes: 20M × 1,536 × 4 ≈ 122.9 GB.
  • This excludes metadata, source text, index overhead, replicas and backups.

The estimate is an order-of-magnitude baseline, not a final infrastructure quote.

Embedding and inference cost

  • Embedding: total tokens processed ÷ 1M × price per million tokens.
  • LLM: input tokens × input rate + output tokens × output rate.
  • Include retries, reranking, query rewriting, tool calls and re-embedding during model migrations.
  • Reduce unnecessary work with deduplication, batching, caching and model routing.

Performance and capacity

  • Ingestion throughput: documents/chunks per second.
  • Queue depth and time-to-index under peak load.
  • Retrieval and reranking latency.
  • End-to-end p50/p95 latency and concurrency.
  • Failure rate, retry volume and worker saturation.

Trade-off decisions

Chunk size and overlap affect both quality and index size. Top-K and context length affect quality, latency and token cost. Larger models may improve some answers but increase cost and latency. Optimise against the business task and risk, not a single benchmark.

08 / INTERVIEW SCRIPT

A 90–120 second answer

Use this structure when asked to walk through how you would design an end-to-end RAG system.

Suggested answer · adapt to the question
“I think about RAG in four layers: data preparation, the online retrieval and generation path, optional tool orchestration, and evaluation and operations.

First, in the offline pipeline, I ingest data from approved sources, parse and clean it while preserving document structure, then split it into chunks. I enrich those chunks with metadata such as source, page, version and access attributes. I generate embeddings and store them in a vector index, often alongside a keyword index so the system can support hybrid search. I would also design incremental updates so changed or deleted documents do not leave stale content behind.

At query time, I understand or rewrite the question, retrieve relevant chunks, apply metadata and permission filters, and optionally rerank the candidates. I then build a context within a token budget and ask the model to answer using that evidence, with citations and an explicit instruction to abstain if the evidence is insufficient. I would validate the answer and citations rather than assuming that a fluent response is a correct one.

Tool calling is a related but separate capability. An agent may call a search, database or business API when it needs live information or needs to perform an action. Those tools need typed argument validation, permission checks, timeouts, audit logs and human approval for consequential actions.

Finally, I evaluate each stage separately: retrieval metrics such as Recall@K or MRR, answer faithfulness and correctness, citation quality, appropriate abstention, tool success, latency and cost. In an enterprise environment, I would also treat access control, provenance, incremental indexing, monitoring and failure recovery as core design requirements—not optional extras.”

Prioritise these topics

Core: ingestion → parsing → chunking → embeddings → indexing; vector vs keyword vs hybrid; retrieval → reranking → context → grounded generation; retrieval vs answer evaluation.

Enterprise: ACL/RBAC, incremental indexing, queues/workers, retry/idempotency, observability and cost control.

Advanced: agentic RAG, MCP/tool calling, query decomposition, rerankers and capacity planning.

Three questions to keep in mind

  1. Can I find the right evidence? Retrieval quality.
  2. Can I generate a trustworthy answer? Grounding, correctness and citations.
  3. Can I do it securely, reliably and at scale? Enterprise engineering.

Be explicit about what you have implemented, what you have evaluated at prototype scale, and what you understand as a design approach.
