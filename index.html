08 / AI EVALUATION

Make AI quality measurable

Use EvidMatch to explain how a representative dataset, repeatable harness and complementary ranking metrics turn AI changes into evidence rather than opinion.

Precision@5

How many are useful?

If labels of 2 or 3 count as relevant and the top-five labels are [1, 3, 2, 0, 3], three of five are relevant: 3 ÷ 5 = 0.60.

It measures the concentration of good results, but ignores their order.

MRR

How soon is the first useful result?

The first relevant result above is at rank 2, so the reciprocal rank is 1 ÷ 2 = 0.50. MRR averages that value across profiles.

It rewards finding one suitable opportunity quickly, but ignores later results.

NDCG@5

Are the best results near the top?

It gives more gain to label 3 than label 2, discounts results lower in the list, then compares the actual order with the ideal order.

1.0 means the ranking matches the best possible ordering.

中文记忆法

Precision@5 看前五名里“好职位有多少”；MRR 看“第一个好职位来得多快”；NDCG@5 同时看“好到什么程度”和“排得够不够靠前”。对 EvidMatch，以 NDCG@5 为主、Precision@5 为辅，MRR 补充衡量首次发现好机会的速度。

Interview answer · ranking evaluation
“For evaluating Quick Match, I would use complementary ranking metrics. Precision at five measures how many of the top five recommendations are relevant according to human-labelled ground truth. MRR measures how early the first relevant result appears. NDCG at five considers both relevance levels and ranking positions, so it rewards systems that put the most relevant jobs nearer the top. For EvidMatch, I would use NDCG at five as the primary ranking metric, supported by Precision at five and MRR.”

Is an evaluation harness just an integration test?

“No. Unit tests check deterministic pieces such as scoring, filters and citation parsing in isolation. Integration tests check that components and external boundaries work together. An evaluation harness runs a versioned set of representative examples through the AI workflow, records outputs and calculates quality metrics. I need all three: tests protect software behaviour, while evals measure probabilistic answer and ranking quality.”

Remember: unit = one deterministic part; integration = connected parts; dataset = examples and labels; harness = run, record and compare; metrics = judge quality.

Do we need to write new Golden Labels for every evaluation run?

“No. I would maintain a versioned golden evaluation dataset, initially using synthetic profiles and human-reviewed relevance labels. The same labels can be reused across many algorithm versions, which gives us a consistent comparison. New human annotation is needed when we add new profiles or jobs, materially change an example, or correct unreliable ground truth—not whenever we change a weight, embedding model or retrieval strategy.”

Dataset strategy: keep a fixed golden test set for regression comparison, a development set for tuning, and a consented real-world feedback set for discovering new failure cases. AI can propose labels and evidence, but a proposed label is not a human-verified Golden Label.

How do content hashing, incremental indexing and batch processing work together?

“For profile knowledge, I hash the canonical chunk content and store the embedding model version. A later run can skip unchanged chunks, regenerate new or changed ones and remove obsolete records, rather than embedding the whole profile again. I process the required work in controlled batches and persist each successful batch. If a request is rate-limited or interrupted, recovery resumes the pending items with bounded retries instead of discarding completed work.”

Important distinction: incremental indexing decides which items need work; batching controls how much work is attempted at once; persisted per-item or per-batch state makes partial recovery possible. Hashing must use stable canonical content, and a model-version change must invalidate otherwise unchanged embeddings.

How did you make OpenAI calls recover safely?

“I centralised OpenAI client creation so the default timeout is 60 seconds per attempt with at most two retries—three attempts in total. One existing job-draft flow keeps its stricter 45-second timeout. I migrated eight call sites across RAG, knowledge embeddings, profile analysis, onboarding and job drafting, and updated nine Vercel functions to package the shared client. Transient 429 and 503 responses are retried, a permanent 400 is not, and an unresponsive service times out rather than hanging indefinitely.”

Recovery semantics: a later failed embedding batch does not return a partial vector set. During knowledge synchronisation, a mid-run failure does not leave a source with no chunks, and a retry does not re-embed sources already completed. Remember that 60 seconds is per attempt: retries and back-off can make the end-to-end request longer and can multiply provider cost.

中文提示：maxRetries: 2 不是总共两次，而是首次调用后最多再试两次，共三次。这里实际列出的是八个调用文件，不要说成七处。

How would you load-test the RAG workflow?

“I would define a realistic concurrency target, test expected and peak traffic, then increase load until the first bottleneck appears. I would track throughput, application errors, 429s, database connections, queue depth, retry volume, token cost and response-time percentiles. P50 represents the typical experience; p95 means 95 per cent of requests completed within that time; p99 exposes the slowest one per cent. I would also inject timeouts and provider failures to verify bounded recovery rather than test only ideal conditions.”

Example acceptance target—not a measured result: 50 concurrent profile-RAG questions, p95 below eight seconds and fewer than 1% application errors while staying within provider rate and cost limits. Do not present this proposed target as current capacity.

Order of work: finish per-request token limits, a system-wide daily kill switch, concurrency control and retry-cost telemetry before a large stress test. Otherwise retries can turn a provider incident into a cost spike.

What did the threshold and K sweep show?

“I added a parameter sweep to run the same labelled cases across controlled threshold and K combinations. K values of three, five and ten made little difference to Hit at one or MRR; they mainly changed prompt size. At the 0.30 floor, K five used about 1,100 characters for Lingyun, compared with about 1,700 at K ten. The floor mattered more: 0.35 reduced Lingyun’s Hit at K from 0.88 to 0.79; 0.25 repaired only some location cases; 0.20 reached 0.96 retrieval recall and repaired all of them, but retrieval rejected only one of six unanswerable questions.”

Decision: do not lower the global floor from one aggregate score. A lower floor moves more cost and safety responsibility to the answer layer.

What did the answer-layer evaluation add?

“The answer harness sends each case through the production retrieval, floor, grounded prompt and citation-filter path, then uses an LLM judge to score refusal, hallucination, false refusal, faithfulness, correctness and citation behaviour. At the 0.30 floor, hallucination was 0.00 on this test set, including false-premise questions about Atlassian and leading a team of twenty. Faithfulness was 0.90 for Lingyun and 0.86 for Aaron. The main measured weakness was false refusal on location-style questions: 0.13 and 0.36 respectively. I would treat those as dataset-specific results, inspect the failure list and use an independent judge model where possible, because the default judge shares the answer model and can have self-preference.”

Why are citations and noAnswer part of quality?

At the 0.30 floor this occurred in three of eight unanswerable cases. I would detect textual refusals consistently, return the correct structured state and evaluate citation hit and precision—not only whether the prose sounds grounded.”

Next steps: evaluate a lower floor only for profile-level questions, classify textual refusals as no-answer, add regression cases for location and false premises, and rerun retrieval plus answer metrics before considering a production configuration change.

09 / COMPLEX DATA AI

Reliable AI over large, complex datasets

A likely technical question: identify the constraints, separate retrieval quality from answer quality, and explain how you would measure the trade-offs.

01 · Scale

Volume & throughput

Large datasets, many file types and continuous ingestion can overwhelm a single-process design. Consider indexing, partitioning, distributed or parallel processing, incremental ingestion and back-pressure.

02 · Latency

Time to useful result

Parsing, embedding, retrieval and generation all add delay. Use asynchronous jobs for long-running work, caching, batching, pre-computation and progressive results where appropriate.

03 · Cost

Cost per document or task

Control compute, storage and LLM inference costs through model selection/routing, token budgets, deduplication, caching and calling expensive models only when they add value.

04 · Accuracy

Retrieval and answer quality

Retrieve the right evidence, preserve context and avoid unsupported conclusions. Evaluate retrieval separately from generation; provide citations and abstain when evidence is insufficient.

05 · Governance

Permissions & traceability

Respect source-level access controls, preserve provenance and audit trails, and ensure the model cannot expose documents the user is not authorised to see.

System objective

Optimise the whole workflow

The goal is not maximum accuracy at any cost. It is a reliable, secure and useful result within acceptable latency and cost, measured against the business outcome.

关键概念要分清

Retrieval accuracy：有没有找到正确的证据？
Answer accuracy / faithfulness：回答是否正确理解证据、没有超出证据范围？
Reliability：证据不足时能否正确 abstain，而不是编造？
Governance：检索是否遵守用户权限，结果能否追溯到原始来源？

Suggested technical answer · approximately 90 seconds
“I think the biggest challenge is balancing scale, response time, cost and reliability rather than optimising only one dimension. First, at the data layer, the system needs to ingest and index large volumes of heterogeneous data efficiently. That may require incremental and distributed processing rather than trying to process everything synchronously. Second, latency matters: parsing, retrieval and LLM inference can make a workflow too slow for users, so I would consider asynchronous processing, caching and pre-computation. Third, inference and infrastructure costs need to be controlled through model selection, token budgets and only using more expensive models where they add measurable value. But none of that matters if the result is wrong. I would evaluate retrieval quality separately from answer quality: did we retrieve the right evidence, and did the model produce a faithful answer supported by that evidence? The system also needs to abstain when evidence is insufficient. Finally, in an enterprise environment, permissions, provenance and auditability are essential. I would measure the trade-offs using throughput, p95 latency, cost per task, retrieval metrics, answer quality, citation accuracy and business outcomes.”

What would you measure?

  • Scale: ingestion throughput, queue depth, processing failures and time to index.
  • Latency: p50/p95 end-to-end latency and time to first useful result.
  • Cost: cost per document, query or completed workflow.
  • Retrieval: Recall@K, Precision@K, MRR or NDCG on labelled cases.
  • Answer: correctness, faithfulness, citation precision and appropriate abstention.
  • Governance: unauthorised retrieval should be zero; audit and provenance should be complete.

Likely follow-up

“If you had to prioritise one challenge, which would it be?”

“I would start with the use case and its risk. For an evidence-led investigation workflow, I would prioritise trustworthy retrieval, permissions and traceability first. Then I would optimise latency and cost against the volume and service-level expectations. A fast, cheap answer is not useful if it is based on the wrong evidence.”

“How would you improve accuracy?”

Inspect failure cases, improve parsing and metadata, tune chunking/indexing and retrieval, rerank where justified, constrain generation to evidence, and run a versioned evaluation set after each change.

Case: EvidMatch AI Match

Mock round 2 · technical delivery · 2–3 minutes
“One of the core AI features I built in EvidMatch is a two-stage job matching system. The design was driven by a practical trade-off between matching quality, response latency and inference cost.

We ingest opportunities from public ATS sources, normalise the job content and create embeddings for semantic comparison. Users build evidence-based portfolios containing their projects, skills and demonstrated experience.

The first stage is Quick Match. It uses hybrid matching—keyword-based scoring together with semantic similarity—to rank opportunities without making a generative LLM call for every job. This gives the user a fast shortlist and avoids paying the latency and token cost of detailed analysis across the full opportunity set.

When a user wants to investigate a particular role, they can request a Detailed AI Match. This second stage uses an LLM to compare the job requirements with evidence from the user’s portfolio. It separates strong matches, partially supported requirements and missing evidence. An important design principle is that the system should not invent qualifications or experience. It can help the user express existing evidence more clearly, but it must identify unsupported requirements as gaps.

The main engineering challenge is balancing usefulness with latency, cost and reliability. I use controlled access to expensive model calls and design the request flow so failures are visible rather than silently producing misleading results. I have now added repeatable retrieval and answer-layer evaluations, which exposed a location retrieval gap and a structured refusal problem. They are early baselines rather than a mature production evaluation platform, but they let me compare targeted changes with evidence instead of anecdotal examples.”
