Engineering methods · interview evidence

Move fast.
Keep control.

A practical playbook for using AI coding tools without outsourcing judgement: define boundaries, deliver one testable slice, enforce trust at the data layer, and leave evidence another engineer can review.

AI accelerates implementation. Humans own the boundaries.

Scope, permissions, sensitive data, production changes and release decisions remain explicit human responsibilities.

01 / APPROACH

Boundary-first engineering

Before choosing a model or generating code, make the product, authority and evidence boundaries concrete.

Scope

Decide what this phase is

Sort work into launch, fast-follow and later. Record what is explicitly excluded so an AI tool cannot quietly expand the solution.

Authority

Map who can see and do what

Turn roles × resources × actions into a permissions matrix. Each meaningful cell becomes a database rule and an allowed or forbidden test.

Evidence

Agree how “ready” will be proved

Define quality, security, latency, cost and operational exit criteria before the POC. A demo is evidence of possibility, not production readiness.

Interview answer · how I start
“I start with the workflow and the boundaries, not the model. I identify the user, the decision or hand-off we are improving, what data is involved, who is allowed to see or change it, and what success and failure would look like. I then define the smallest slice that can test the risky assumption. That gives the AI implementation context, but it also gives the team a clear basis for reviewing whether the result is useful, safe and worth extending.”

02 / DELIVERY

One independently testable slice at a time

Keep each change small enough to understand, verify and reverse without mixing unrelated risk.

Write the current state

Record the current slice, branch or PR, next step, decisions, blockers and environment facts. The next human or AI session should not reconstruct intent from chat history.

Implement one concern

Use one focused branch and one independently reviewable commit. Reuse the existing architecture and avoid speculative abstraction.

Prove both sides

Test the intended path and the forbidden or failure path. Never weaken a test merely to obtain a green build; classify the failure first.

Leave a truthful hand-off

Report exactly what changed, what passed, what failed, what was not run and whether anything was pushed, deployed or changed in production.

Recent EvidMatch example: retrieval evaluation, answer-layer evaluation and recovery work were kept in separate focused changes. Production RAG_CONFIG was not changed; unrelated matching-eval failures were reproduced with the recovery change staged out rather than hidden or “fixed” opportunistically.
03 / AI WORKFLOW

From AI-assisted coding to a controlled delivery system

My current Claude Code workflow, developed through DrainWise, treats the model as an implementation partner inside an engineering system—not as an autonomous owner of the product or release.

Memory

Persistent project context

CLAUDE.md holds the project brief, glossary, UI conventions and durable rules. A separate hand-off file records the current goal, decisions, state, blockers and gotchas so a fresh session can resume without relying on chat history.

Workflow

Methods loaded when needed

Skills provide repeatable procedures and expected outputs. They are not another always-on instruction dump: use research, planning, TDD, debugging, security review or hand-off when the current stage calls for it.

Enforcement

Hooks and CI create hard gates

Hooks can block dangerous Git actions, PR creation before required checks, and merges without green CI. GitHub Actions and branch protection provide an independent backstop that a coding agent cannot talk its way past.

Division of labour

Fresh-context, read-only reviewers

Separate reviewers inspect behaviour, accessibility/UI, UX flow and visual design. They report findings rather than editing the implementation. UI/UX/design reviews run only after I explicitly approve them.

Nine stages, with a gate before moving on

01 · Init

Prepare the project

Check repository instructions, hooks, CI and the issue/ticket tracker. Confirm the working tree and current state.

02 · Think

Research and decide

Use primary sources for unknown facts. Make product and technical decisions explicitly; capture terms and constraints in the glossary.

03 · Map

Record the plan

Maintain a decision map and create tickets for unresolved choices. Turn agreed decisions into a spec and thin, independently deliverable tickets.

04 · Slice

One ticket, one branch

Define scope, affected files and acceptance criteria. Keep each slice small enough for one focused PR and a meaningful review.

05 · Build

Test first, then implement

Write or confirm the failing test, identify module seams and implement the smallest change. Diagnose causes rather than patching symptoms.

06 · Pre-PR

Simplify and inspect

Remove needless complexity, run security checks where relevant, and use independent reviewers. UI critique and browser review are explicit approval gates.

07 · Review

Resolve findings

Review standards and specification compliance. Do not proceed with open findings above the agreed low-severity threshold.

08 · Merge

Require objective evidence

CI must be green and the PR must record smoke-test evidence. A hook blocks the merge when either condition is missing.

09 · Post-merge

Verify and update memory

Re-run relevant tests on the main branch, update the decision map and hand-off, and record any new operational gotcha. Stages 5–9 repeat for each ticket.

Choose the right lever for the job

CLAUDE.mdFacts and rules that should be available in every session: project context, conventions, constraints and commands.
SkillsOn-demand playbooks: research, decision discovery, architecture mapping, ticket slicing, TDD, debugging, simplification, security review and hand-off.
HooksDeterministic reminders or blockers at the point of action—for example, dangerous Git commands, PR creation and merge checks.
SubagentsFresh-context workers with limited tools. Review agents are read-only so they cannot quietly change the code they are meant to assess.
MCP / integrationsLive access to tools such as the browser, database and deployment platform. Tool access is scoped; it does not replace authorisation or human approval.

CI and release controls in DrainWise

  • Every PR runs three parallel jobs: web lint/typecheck, planner Vitest and Python pytest for the model/API.
  • Main branch protection requires a PR and the checks; force-push and branch deletion are disabled.
  • A pre-merge hook checks GitHub CI status and requires smoke-test evidence in the PR description.
  • Vercel deploys from GitHub after merge; I do not run an ad-hoc deploy script.

Parallel work without parallel authority

  • Independent tickets can run in separate Git worktrees, each with its own brief, branch and PR.
  • Each session runs its own review and records findings on its PR.
  • I retain ticket prioritisation, merge decisions and real-device acceptance testing.
  • Parallel agents increase throughput; they do not receive authority to approve or release their own work.
DrainWise is the running case study, not a claim of enterprise production maturity. It is a City of Parramatta hackathon entry using sample data and a risk model trained on simulated history. Its stack has a Next.js frontend, FastAPI risk API and TypeScript planner; a parity test checks that Python and TypeScript risk scores stay within 1e-6. Authentication was deliberately left out of the MVP: a short team code shares a session, with known limits such as last-write-wins. Supabase RLS is enabled with no client policies; the server route uses the server key. The workflow makes these decisions and limitations visible rather than describing the demo as production-ready.
Interview answer · how I use AI coding agents now · 90 seconds
“My approach has evolved from asking an AI tool to implement a feature to giving it a controlled delivery process. I keep durable project context and conventions in a repository instruction file, while repeatable methods—such as research, planning, test-driven development, debugging and hand-off—are loaded as skills when needed. For a larger change, I first research the unknowns, record decisions, map the work into small tickets and then implement one ticket per branch and PR. I use hooks for deterministic gates, such as blocking a merge unless CI is green and smoke-test evidence is recorded. I also use fresh-context, read-only reviewers so the agent that wrote the code is not the only one assessing it. CI runs the relevant frontend, planner and Python tests, and I still own the product decisions, review findings, merge decision and real-device checks. DrainWise is where I have put this workflow into practice. It is a hackathon project with sample data, so I am careful to distinguish the engineering controls I have implemented from production capabilities I have not built, such as full authentication and concurrent-write handling.”

04 / TRUST

Enforce trust below the browser

UI filtering improves experience; it is not an authorisation boundary. Sensitive access belongs in database policies and controlled server operations.

Least privilege

Deny until the relationship is explicit

RLS needs an ownership or relationship condition, not simply “authenticated”. Do not create write policies until the permissions matrix requires them.

Controlled transitions

Protect sensitive state changes

Marks, roles, consent, publication and other sensitive fields change through validated functions or restricted APIs. Multi-record actions remain one transaction.

Data minimisation

Collect with a purpose and deletion path

For every personal field, record why it exists, where it lives, who can access it, retention and deletion triggers. Secrets and service credentials stay server-side.

Interview answer · secure AI delivery
“I do not rely on the browser to hide sensitive data. I start with a permissions matrix, enforce the relationship in the database or server boundary, and add direct negative tests for another user, an unrelated role and an anonymous caller. Sensitive transitions go through a controlled operation that derives the actor from the authenticated session and validates the current state. That means a UI regression or a hand-crafted request cannot silently bypass the rule.”
05 / AI CONTROLS

Turn guidance into enforcement

Use the strongest mechanism that matches the risk. Add automation to prevent a real recurring failure, not because the tool exists.

1 · Deny ruleFor commands that must never run automatically: production database pushes, production deploys, force pushes or secret-file reads.
2 · Blocking hookFor a cheap, deterministic check that is easy to forget. Match narrowly, fail with a clear reason and keep it fast.
3 · Specialist reviewerFor a heavy independent check. Give a security reviewer read-only tools, a fresh context and a ranked reporting format; keep the writer separate from the reviewer.
4 · Skill / runbookFor a repeatable multi-step procedure with explicit approval gates, such as hand-off, migration deployment or smoke testing.
5 · Repository instructionFor persistent context and rules: current scope, security patterns, commands, research gates and human-owned paths.
中文记忆法规则强度从“机器直接阻止”逐渐到“提醒 AI 遵守”。危险越高、判断越确定，越应靠 deny rule、hook、数据库约束或 CI，而不是只写一句提示词。
06 / PROOF

Different risks need different evidence

A green unit test cannot prove RAG quality, cross-user isolation, recovery behaviour or production capacity.

Software correctness

  • Unit tests for deterministic logic.
  • Integration tests for component and SDK boundaries.
  • Allowed and forbidden database tests for authorisation.
  • Build, type-check and focused regression tests.

AI quality

  • Versioned golden datasets, synthetic breadth and human-reviewed labels.
  • Retrieval and answer-layer metrics, plus inspected failure cases.
  • Independent judge models where practical.
  • No production claim from a small benchmark.

Reliability and cost

  • Bounded timeout and retry behaviour; test 429, 503, 400 and non-response.
  • Atomic output and resumable completed work.
  • Per-request token limits, concurrency controls and a daily kill switch.
  • Load-test staging at agreed peak multiples with p50/p95/p99 and error budgets.

Launch readiness

  • Evidence-linked checklist, not a verbal “looks ready”.
  • Backups plus a restore drill, monitoring and rollback.
  • Accessibility, privacy, security and operational ownership.
  • Human approval for production and high-risk paths.
Interview answer · moving a POC towards production
“I separate proof of usefulness from proof of operability. A POC first needs representative quality evidence and clear failure categories. Before production, I also need authorisation tests, bounded recovery, observability, cost controls, load and restore tests, a rollback plan and a named operational owner. I use a checklist with links to the evidence, and unticked high-risk items remain blockers unless an accountable owner explicitly accepts the risk.”
07 / FOLLOW-UPS

Answers for deeper questioning

Keep the principle short, then attach one concrete example.

How do you stop AI-generated scope creep?

“I write the current slice and its explicit exclusions into repository context, then keep one concern per branch and PR. If the implementation uncovers a later feature, I record it rather than quietly building it. That keeps review meaningful and makes it easy to distinguish necessary supporting work from product expansion.”

When do you stop and research instead of coding?

“I use a research gate when a decision affects authentication, security, an unfamiliar external contract or a broad architectural choice. I state what is known, what evidence is missing and what decision the research will unlock. That prevents confident implementation based on an assumption, while also stopping open-ended research from consuming the delivery window.”

How do you review work produced with AI?

“I review the trust boundaries and failure behaviour, not only the happy-path diff. I run the focused tests first, then use an independent reviewer for sensitive changes with read-only access and a required severity-based report. The author does not silently rewrite the reviewer’s findings, and the final hand-off names both the evidence and the gaps.”

How do you make patterns reusable across rotations?

“I separate durable patterns from project-specific state. Approved security recipes, test shapes and runbooks become reusable assets; current branches, blockers and next steps stay in the hand-off. I would share a pattern only after it solved a real problem and was reviewed, so the library compounds learning without turning one project’s assumptions into a universal rule.”

What is the honest maturity boundary?

“I have used these methods in focused product and RAG work: small changes, explicit production boundaries, direct negative tests, measured evaluation and truthful failure reporting. The full starter kit is a design and template set, not evidence that every guardrail has been deployed in every project. I would describe the implemented control, the proposed next control and the production state separately.”
